## Problem Statement

### What pain point are we solving?
When users file issues on line-cook's GitHub repo, there's no automated first-responder. Issues sit until a human reads them, understands the problem, investigates the codebase, and responds. For issues with clear code-level causes (typos, broken imports, logic errors), an AI agent could analyze the codebase, propose a fix on a test branch, and comment back with instructions — dramatically reducing response time from hours/days to minutes.

### Who experiences this pain?
- **Issue reporters** waiting for acknowledgement and a fix
- **Maintainers** spending triage time on issues that could be auto-diagnosed

### What happens if we don't solve it?
Issues accumulate without response, contributors feel ignored, and maintainer time is spent on mechanical triage work that could be automated.

## User Perspective

### Primary User
Open-source contributors who file issues on the line-cook repo, and the maintainer (Sam) who triages them.

### User Context
- Contributors know how to file GitHub issues but may not know the codebase internals
- They expect some response within a reasonable timeframe
- The maintainer already uses Claude Code locally and understands AI-assisted workflows

### Success Criteria (User's View)
- **Reporter:** Files an issue → gets an automated response within minutes. If the problem is clear, receives a link to a test branch with fix + instructions to verify. If unclear, gets targeted clarifying questions.
- **Maintainer:** Sees issues pre-triaged with analysis. Clear-fix issues already have proposed branches ready for review. Saves significant triage time.

## Technical Exploration

### Existing Patterns in Codebase

| Pattern | Location | Relevance |
|---------|----------|-----------|
| GitHub Actions hardening | `.github/workflows/*.yml`, ADR-0013 | Must follow: explicit permissions, timeouts, concurrency, path filters, pinned versions |
| Release workflow with `gh` CLI | `.github/workflows/release.yml` | Pattern for `gh release create` with dynamic content — similar to `gh issue comment` |
| Validate workflow | `.github/workflows/validate.yml` | Pattern for Python script execution in CI |
| Template-sync architecture | `core/templates/`, ADR-0003/0011 | If generalizing later, agent prompts should live in templates |
| CLAUDE.md project context | `CLAUDE.md`, `AGENTS.md` | Auto-loaded by `claude-code-action` — gives the agent project knowledge for free |
| Phase-specialized agents | ADR-0006 | Existing pattern of specialized review agents with structured verdicts |

### External Approaches Researched

| Approach | Source | Trade-offs |
|----------|--------|------------|
| `anthropics/claude-code-action` | Official Anthropic action | Full Claude CLI in CI, auto-reads CLAUDE.md, supports interactive (@mention) and automation modes. The clear winner for this project. |
| Probot (GitHub App) | probot/probot | Persistent server, cross-repo. Overkill for a single repo. |
| Raw Anthropic API in workflow | Direct curl/script | More control, much more setup. No tool access without building it. |
| `peter-evans/create-pull-request` | Popular action | Higher-level branch+PR creation. Useful downstream but doesn't solve the analysis part. |

### Constraints from Architecture

- **ADR-0013 applies**: Any new workflow must include explicit permissions, timeout, concurrency group, and follow established hardening patterns
- **GITHUB_TOKEN limitations**: Commits made with GITHUB_TOKEN don't trigger downstream workflows. If the fix branch needs CI to run, we'll need a GitHub App token via `actions/create-github-app-token`
- **Authentication**: Claude Max subscription supported via `claude_code_oauth_token` (generated by `claude setup-token`). Alternative: `ANTHROPIC_API_KEY` for pay-per-token.
- **Cost awareness**: With Max subscription, no per-call cost — but `--max-turns` still needed to prevent runaway sessions eating subscription quota

## Technical Approaches Considered

### Option A: claude-code-action with dual-mode triggers (Recommended)
**Description:** A single GitHub Actions workflow using `anthropics/claude-code-action@v1` that triggers on both `issues: [opened]` (auto-triage) and `issue_comment: [created]` (interactive @mention). The action gets full Claude CLI access with tool restrictions (`--allowedTools`). For clear fixes, Claude creates a branch, commits a fix, and comments with instructions. For unclear issues, it asks clarifying questions as a comment.

**Pros:**
- Official Anthropic action — maintained, documented, tested
- Auto-reads CLAUDE.md and AGENTS.md — agent understands the project
- Full tool access (Read, Grep, Glob, Bash) scoped by `--allowedTools`
- Interactive mode for follow-up conversations via @mention
- Single workflow file, minimal setup

**Cons:**
- API cost per issue (mitigated by `--max-turns`)
- GITHUB_TOKEN can't trigger downstream CI on created branches
- Dependent on Anthropic maintaining the action

**Effort:** Low

### Option B: Custom Python script + Anthropic API
**Description:** A Python script in `dev/` or `.github/scripts/` that calls the Anthropic API directly, analyzes the issue, searches the codebase using local tools, and comments back.

**Pros:**
- Full control over prompting and behavior
- No dependency on third-party action
- Can embed line-cook-specific logic

**Cons:**
- Must reimplement tool access (file reading, code search)
- Must handle GitHub API interactions manually
- Significant development and maintenance burden
- No interactive follow-up without building a state machine

**Effort:** High

### Option C: claude-code-action + GitHub App token for CI triggering
**Description:** Same as Option A, but adds a GitHub App for authentication so that fix branches trigger CI. Requires creating a GitHub App, storing its credentials, and using `actions/create-github-app-token`.

**Pros:**
- Fix branches get full CI (validate, typecheck)
- Bot appears as a named identity, not "github-actions[bot]"
- Enables future cross-repo expansion

**Cons:**
- Requires creating and maintaining a GitHub App
- More secrets to manage (APP_ID, APP_PRIVATE_KEY)
- Added complexity for a feature that may not need CI on fix branches initially

**Effort:** Medium

## Risks and Unknowns

### Technical Risks
| Risk | Likelihood | Impact | Mitigation |
|------|------------|--------|------------|
| Claude proposes incorrect fix | M | H | Explicit "test branch" framing — user must verify before merging. Never auto-merge. |
| Runaway usage from spam issues | L | M | `--max-turns 10` limit, rate limiting via concurrency group, ignore bot-created issues |
| Claude modifies unrelated files | L | H | Scope `--allowedTools` to read-only + targeted git/gh commands |
| GITHUB_TOKEN can't push to protected branches | M | L | Fix branches target non-protected branch names (`fix/issue-NNN`) |
| Issue body contains prompt injection | M | M | Claude Code has built-in injection resistance; CLAUDE.md instructions override |

### Dependency Risks
- `anthropics/claude-code-action` is maintained by Anthropic — low risk of abandonment but breaking changes possible
- OAuth token is a secret — if compromised, attacker could run Claude sessions against this repo (token lasts ~1 year)
- GitHub Actions runners have network access — Claude could theoretically make external requests

### Scope Risks
- Temptation to make the agent "smart enough" to handle all issue types — should start with clear code-level bugs only
- Generalizing for other repos too early — start line-cook-specific, extract patterns later
- Auto-fix quality: even "clear" fixes may be wrong. Must never auto-merge.

### Open Questions

- [ ] What `--allowedTools` scope is safe? Read-only + `gh issue comment` + `git checkout -b` + `git push`?
- [ ] Should the agent create a PR or just a branch? (PR is more discoverable, branch is lower-commitment)
- [ ] What model to use? Sonnet for speed or Opus for better analysis? (Max subscription covers both)
- [ ] Should the auto-triage on `issues: [opened]` always run, or only when certain labels/keywords are present?
- [ ] How to handle issues that are feature requests, not bugs? (Probably just label and skip)

## Recommended Direction

### Chosen Approach
**Option A: claude-code-action with dual-mode triggers**, starting line-cook-specific. This gives us the most capability with the least effort, leveraging Anthropic's official action and the existing CLAUDE.md/AGENTS.md context.

### Rationale
- The official action handles all the hard parts (tool access, context loading, GitHub integration)
- Dual-mode (auto-triage + @mention) covers both the "new issue" and "follow-up" use cases
- Starting without a GitHub App keeps complexity low; we can add it later if CI-on-fix-branches becomes important
- Line-cook already has strong CLAUDE.md project context, which the action reads automatically

### Suggested Scope
| Scope | Recommendation |
|-------|----------------|
| MVP | Single workflow: auto-triage new issues with analysis comment. No branch creation yet. Classify as bug/feature/question, add labels, ask clarifying questions if unclear. |
| Full Feature | Add branch creation for clear fixes. Comment with test instructions and branch link. Interactive @mention support for follow-up. |
| Epic | Generalize into a reusable template/spice. GitHub App token for CI triggering. Cross-repo support. PR creation instead of branches. |

### Deferred Items
- GitHub App token / named bot identity
- Auto-PR creation (start with branches, graduate to PRs)
- Cross-repo generalization / spice packaging
- Cost monitoring dashboard
- Integration with beads (auto-create bead from triaged issue)
